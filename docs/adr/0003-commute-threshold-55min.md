# 通勤目标与阈值:到公司地址(晴海1-8-10)门到门 ≤70 分

> 文件名沿用 0003(原为 …-55min),内容已演进到下述最终决策;阈值演变史保留在文末。

## 决策

命中条件 #1 的「通勤」**目标是公司地址 `東京都中央区晴海1-8-10`(晴海トリトンスクエア)**,而非单一车站。该地址周边有**多个接入口**:勝どき駅(徒歩约8~9分)、月島駅(徒歩13分)、新豊洲駅(徒歩16分)、楼下**晴海BRT**(徒歩1分,新橋→晴海约12分)。计算団地通勤时取这些接入口里**最快**的。

**watchlist = 到该地址门到门 ≤ 70 分的神奈川団地集合**。在**全 166 個神奈川団地**上扫描(而非只在早期 43 候选上),筛出 **31 個団地**(川崎市 11 + 横浜市 20,覆盖川崎/鶴見/神奈川区/中区/南区/保土ヶ谷/西区/都筑/青葉等)。完整实测数据见 `.scratch/ur-vacancy-alert/data/commute_to_katsudoki.md`。

## 计算口径

每個団地:`门到门 = 最寄り駅徒歩/バス(UR traffic) + 该站→勝どき(乗換案内实测最速) + 勝どき→办公室徒歩9分`。各站→勝どき 时间逐一拉 Yahoo!路線情報**实际路线页**取得(不信搜索摘要)。

该口径**保守**:未计入楼下晴海BRT(经新橋可比绕勝どき快几分),所以 71~73 分的边界団地(虹ヶ丘/睦町/すすき野/山田富士公園/コンフォール南日吉/能見台イースト 等)用 BRT 很可能其实 ≤70,如需可单独用 BRT 路由核入。

取舍依据:watchlist 的**漏报(砍掉其实够近的団地)代价高**(静默错过房源),**误报(多收稍远団地的通知)代价低**(看一眼忽略),故阈值附近偏向纳入,阈值本身也取较宽的 70。

## 阈值演变史

1. PRD 初版:到**勝どき駅**换乘 ≤40 分。实测发现勝どき仅大江戸線一条线、神奈川方向普遍偏远,≤40 分**仅剩 1 個**(小杉御殿),失去意义。
2. 放宽到勝どき门到门 ≤55 → 一度筛出 18 個,但那批"站→勝どき"取自 WebSearch 摘要、严重偏乐观(如武蔵小杉摘要 29 分、实际 41 分);逐站拉实际路线页重核后修正为 **14 個**(剔除横浜/神奈川区若干、纳入被低估的川崎旭町ハイツ/鶴見町第二/ミラリオ大師河原)。
3. 用户澄清:公司其实在 **晴海1-8-10**(勝どき与月島之间),要求按**地址**算、且把**附近所有车站/BRT**都纳入,阈值 ≤70。遂改为上述地址口径,在全 166 上扫描 → **31 個**。

教训:① 通勤分钟必须以乗換案内实际路线页为准;② 目标是"地址"而非"最近的某一个站",要考虑地址周边全部接入口;③ 宽阈值下必须扫全量,早期为紧目标做的地理预筛会漏掉"快速线路够得着的"远站(如戸塚/金沢文庫/あざみ野/新百合ヶ丘等到勝どき其实 55~61 分)。

## Consequences

- `watchlist.json` 含 31 個団地,每項带 `commute_min`(到晴海办公室门到门分钟)便于追溯与重排。
- 命中条件 #1、CONTEXT、邮件正文条件行均已同步为「晴海オフィス ≤70分(门到门)」。
- 电车时刻表少变,偶尔重算即可(重跑 `commute_to_katsudoki.md` 的调研)。
